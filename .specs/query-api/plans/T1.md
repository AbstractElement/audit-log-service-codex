# T1 — Flyway V3: add new keyset indexes (additive only)

*Introduce the two composite indexes that make keyset pagination index-bounded. No drops in this PR.*

## Why this task exists

The `GET /audit-events` endpoint is being switched from offset to keyset
pagination (T6). Keyset ordering is `(event_timestamp DESC, id DESC)`. The
existing indexes
`idx_audit_events_actor_timestamp (actor, event_timestamp DESC)` and
`idx_audit_events_resource_timestamp (resource, event_timestamp DESC)` —
created in `V1__create_audit_events.sql` — let PostgreSQL serve the timestamp
predicate but not the `(timestamp, id)` keyset compare in a single index seek;
each same-millisecond tie would require a heap visit, which breaks the p95
budget at 50M rows.

This task ships the **additive** half of the schema work: two new
`(filter, event_timestamp DESC, id DESC)` indexes that include `id` as a
trailing key column. The legacy indexes stay in place until T7 drops them —
that way an emergency revert of any later task (T4–T6) leaves the schema in
a safe, fully-supported state.

T1 has no dependencies and can ship before any code change.

## Requirements covered

- **AC-3.2** (Ubiquitous) THE SYSTEM SHALL execute queries through the
  existing composite indexes `idx_audit_events_actor_timestamp` and
  `idx_audit_events_resource_timestamp`, verified with `EXPLAIN ANALYZE` on a
  50M-row dataset.

  > Note: the AC text references the *old* index names; this design supersedes
  > those with the new `(actor, event_timestamp DESC, id DESC)` /
  > `(resource, event_timestamp DESC, id DESC)` composites added here. The
  > intent — "queries run through a composite index, verified by
  > EXPLAIN ANALYZE" — is what T1 preserves. T9 discharges the 50M-row part
  > of the AC.

## Design references — extracts inlined

### Indexes → New indexes (Flyway `V3__refine_query_indexes.sql`)

```sql
CREATE INDEX CONCURRENTLY idx_audit_events_actor_ts_id
  ON audit_events (actor, event_timestamp DESC, id DESC);

CREATE INDEX CONCURRENTLY idx_audit_events_resource_ts_id
  ON audit_events (resource, event_timestamp DESC, id DESC);
```

Including `id` as the trailing key column lets the keyset compare be served
entirely from the index without a heap visit per row to resolve same-instant
ties — the dominant cost driver for AC-3.1.

`CONCURRENTLY` keeps ingest available during the migration. Flyway must run
this migration outside a transaction (`-- transactional: false` directive
or Spring Flyway property) because `CREATE INDEX CONCURRENTLY` cannot be
wrapped in a transaction.

## Current state

- `src/main/resources/db/migration/V1__create_audit_events.sql` — creates
  `audit_events` and `audit_events_archive`; declares three indexes on
  `audit_events`:
  - `idx_audit_events_actor_timestamp` on `(actor, event_timestamp DESC)`
  - `idx_audit_events_resource_timestamp` on `(resource, event_timestamp DESC)`
  - `idx_audit_events_timestamp` on `(event_timestamp DESC)`
- `src/main/resources/db/migration/V2__prevent_audit_event_updates.sql` —
  trigger + function that rejects UPDATE on `audit_events`.
- `src/main/resources/application.yml` — no `spring.flyway.transactional`
  key set; Flyway defaults to `true`, which would break
  `CREATE INDEX CONCURRENTLY`.
- `src/test/java/com/auditlog/infrastructure/persistence/AuditEventPersistenceIntegrationTest.java`
  bootstraps PostgreSQL 16 via Testcontainers and lets Flyway apply every
  migration on startup.

## Target state

- New migration file `V3__add_keyset_indexes.sql` exists and is applied by
  Flyway on every fresh boot of the schema.
- `application.yml` carries `spring.flyway.transactional: false` (or
  per-migration directive) so `CREATE INDEX CONCURRENTLY` does not abort.
- `audit_events` now has **5** indexes: the original three plus the two new
  composites. No index is dropped in this PR.
- All existing tests still pass; no production code changes.

## Implementation plan

1. **Configure Flyway to skip the wrapping transaction.**
   - Edit `src/main/resources/application.yml`. Under `spring.flyway` add
     `transactional: false`.
   - Alternative (per-migration): put `-- transactional: false` as the first
     line of the V3 SQL file. Pick the global property — it's a single key,
     and future `CONCURRENTLY` migrations get it for free.
   - Verify the property is recognized: `./gradlew build -x test`. Spring
     Boot 3.5.6 ships flyway-core 10.x which accepts `transactional`.
   - **Edge case**: if `application-test.yml` or another profile overrides
     `spring.flyway`, set the key there too. (Quick grep:
     `grep -rn 'spring\.flyway' src/main/resources src/test/resources`.)

2. **Create the V3 migration file.**
   - Path: `src/main/resources/db/migration/V3__add_keyset_indexes.sql`.
   - Contents:
     ```sql
     -- V3: add composite indexes covering keyset pagination on
     -- (filter, event_timestamp DESC, id DESC). Including id as the trailing
     -- key column lets PG serve the (timestamp, id) tiebreaker compare
     -- entirely from the index, avoiding a heap visit per same-millisecond
     -- row. See .specs/query-api/design.md → Indexes for rationale.

     CREATE INDEX CONCURRENTLY idx_audit_events_actor_ts_id
       ON audit_events (actor, event_timestamp DESC, id DESC);

     CREATE INDEX CONCURRENTLY idx_audit_events_resource_ts_id
       ON audit_events (resource, event_timestamp DESC, id DESC);
     ```
   - **Edge case**: `CREATE INDEX CONCURRENTLY` cannot run inside a
     transaction. The previous step is what makes this legal; if it was
     skipped, Flyway will fail with
     `ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block`.
   - **Edge case**: do **not** drop the old indexes here. T7 owns that.

3. **Run the integration suite against the new migration.**
   - `./gradlew integrationTest --tests AuditEventPersistenceIntegrationTest`.
   - Testcontainers boots a fresh PG 16 and Flyway applies V1, V2, V3 in
     order. Expect a green run with no test changes.
   - If the run fails with a Flyway transactional error, recheck step 1.
   - If the run fails because Testcontainers re-uses a database whose schema
     is at V2 (it shouldn't on a fresh container, but with reuse enabled it
     can), force a fresh container.

4. **Sanity-check the index list.**
   - Drop into the running Testcontainers PG (or stand up a throwaway
     container manually) and execute `\d+ audit_events` (or
     `SELECT indexname FROM pg_indexes WHERE tablename = 'audit_events';`).
   - Expect exactly 5 indexes: `audit_events_pkey`,
     `idx_audit_events_timestamp`, `idx_audit_events_actor_timestamp`,
     `idx_audit_events_resource_timestamp`,
     `idx_audit_events_actor_ts_id`, `idx_audit_events_resource_ts_id`.

5. **Confirm no regression elsewhere.**
   - `./gradlew unitTest archUnitTest` — both should be green; no code
     changed.
   - `./gradlew spotlessCheck` if Spotless is enabled (it is — googleJavaFormat
     1.22.0 per `build.gradle.kts`).

## Test plan

- **Existing tests are the test plan.** No new test class is required.
  The integration suite (`AuditEventPersistenceIntegrationTest` and any
  other `*IntegrationTest`) re-applies Flyway on every container start;
  green = migration is well-formed.
- *Optional, recommended:* add a single assertion inside an existing
  integration test that queries `pg_indexes` for `audit_events` and asserts
  the presence of both new index names. Keeps regression-coverage local.

## Dependencies + rollback

- **Dependencies.** None. Can ship before any code change.
- **Rollback.** `DROP INDEX CONCURRENTLY idx_audit_events_actor_ts_id;` and
  `DROP INDEX CONCURRENTLY idx_audit_events_resource_ts_id;` either as a
  hot-fix migration (`V3_1__rollback_keyset_indexes.sql`) or run manually
  in psql; revert the `application.yml` change. No schema-shape change is
  introduced, so rollback is safe.
