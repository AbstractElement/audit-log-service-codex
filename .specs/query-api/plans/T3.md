# T3 — Cross-field validation for `AuditEventQuery`

*Implement every rule in the design's Validation rules table on
`AuditEventQuery`, returning a typed validation error.*

## Why this task exists

`AuditEventQuery` (added in T2) is a passive record — its ctor accepts any
combination of nulls. The business rules that decide whether a request is
shaped well enough to reach the database (at least one of actor/resource,
`from < to`, window ≤ 7 days, etc.) live in the *Validation rules* table of
the design.

Those rules need to be:

1. **Application-layer, not controller-layer**, so they can be unit-tested
   without spinning up Spring MVC (AC-5.1).
2. **Strictly typed**, so the API layer in T6 can map each failure to a
   stable error code (`MISSING_FILTER`, `WINDOW_TOO_LARGE`, …) without
   string-matching exception messages.
3. **Independent of the cursor path**, because when a cursor is present the
   filters live inside the cursor envelope, not on the request — T5 will
   route cursor requests through `AuditEventCursor.decode` instead of
   `validate()`.

This task adds the validation machinery (`ValidationError`,
`ValidationException`) and the `AuditEventQuery.validate()` method, plus a
unit-test row for every entry in the table. No production caller invokes
`validate()` yet; that wires up in T5.

## Requirements covered

- **AC-1.3** (Unwanted) IF `from` is missing OR `to` is missing OR both are
  missing, THEN THE SYSTEM SHALL return HTTP 400 with a body identifying the
  missing parameter(s).
- **AC-1.4** (Unwanted) IF neither `actor` nor `resource` is supplied, THEN
  THE SYSTEM SHALL return HTTP 400 with a body stating that at least one of
  `actor` or `resource` is required.
- **AC-1.5** (Unwanted) IF `from` is after `to`, THEN THE SYSTEM SHALL return
  HTTP 400.
- **AC-1.6** (Unwanted) IF `to − from` exceeds 7 days, THEN THE SYSTEM SHALL
  return HTTP 400 with a body stating the 7-day cap.
- **AC-1.7** (Unwanted) IF `from` or `to` is not a valid ISO-8601 UTC instant,
  THEN THE SYSTEM SHALL return HTTP 400.

  > Note: ISO-8601 parse failures surface at the API binding boundary, not
  > inside `validate()`. T6's `GlobalExceptionHandler` translates
  > `MethodArgumentTypeMismatchException` → `INVALID_TIMESTAMP`. T3 does
  > not implement this branch but the table row is included so the API
  > layer knows it owns it.
- **AC-2.4** (Unwanted) IF a `cursor` is supplied together with any of
  `actor`, `resource`, `from`, or `to`, THEN THE SYSTEM SHALL return HTTP 400.
- **AC-2.5** (Unwanted) IF the supplied `cursor` is malformed, tampered, or
  not parseable, THEN THE SYSTEM SHALL return HTTP 400.

  > Note: cursor parse failures are raised by `AuditEventCursor.decode`
  > (T2), not by `validate()`. T5 routes them. The table row is included
  > so the error code is visible in one place.
- **AC-2.6** (Ubiquitous) THE SYSTEM SHALL default `limit` to 100 and cap it
  at 500.

  > Note: defaulting (null → 100) is an API-layer concern in T6; `validate()`
  > only enforces the upper/lower bound on the resolved value.
- **AC-2.7** (Unwanted) IF `limit` exceeds 500 OR is less than 1, THEN THE
  SYSTEM SHALL return HTTP 400.

## Design references — extracts inlined

### Validation rules (full table)

| # | Rule | Source AC | Failure mode |
|---|------|-----------|--------------|
| 1 | `cursor` supplied alongside any of `actor`/`resource`/`from`/`to` | AC-2.4 | `400` `CONFLICTING_PARAMETERS` |
| 2 | Either `actor` or `resource` non-blank (when no cursor)          | AC-1.4 | `400` `MISSING_FILTER` |
| 3 | `from` supplied (when no cursor)                                 | AC-1.3 | `400` `MISSING_PARAMETER`, `field = "from"` |
| 4 | `to` supplied (when no cursor)                                   | AC-1.3 | `400` `MISSING_PARAMETER`, `field = "to"` |
| 5 | `from`, `to` parse as ISO-8601 UTC                               | AC-1.7 | `400` `INVALID_TIMESTAMP` — raised at API binding boundary, not here |
| 6 | `from < to`                                                      | AC-1.5 | `400` `INVALID_TIME_WINDOW` |
| 7 | `to − from ≤ Duration.ofDays(7)`                                 | AC-1.6 | `400` `WINDOW_TOO_LARGE` |
| 8 | `1 ≤ limit ≤ 500`                                                | AC-2.6, AC-2.7 | `400` `LIMIT_OUT_OF_RANGE` |
| 9 | `cursor` parses as base64-url JSON, version 1                    | AC-2.5 | `400` `INVALID_CURSOR` — raised by `AuditEventCursor.decode`, not here |

Bean Validation handles single-field shapes (`@Min`, `@Max` on `limit`,
`@Pattern` on the timestamp formats). Cross-field rules are enforced inside
the Application service via a dedicated `AuditEventQuery.validate()` step.

## Current state

- `com.auditlog.application.AuditEventQuery` exists (added in T2), with no
  validation in the ctor and a `withFilters(...)` helper for T5.
- The domain layer uses `IllegalArgumentException` for invariants
  (`AuditEvent.java` constructor). There is no `Result<T, E>` precedent,
  no `ValidationException`, no `ValidationError` record.
- The API layer has **no** `@RestControllerAdvice` yet (T6 will add one);
  if `validate()` throws, no Spring layer is currently positioned to
  translate it. That's fine — `validate()` has no production caller in
  this PR.

## Target state

- New file `src/main/java/com/auditlog/application/ValidationError.java`
  (record).
- New file `src/main/java/com/auditlog/application/ValidationException.java`
  (`RuntimeException` carrying a `ValidationError`).
- `AuditEventQuery` gains a `validate()` instance method.
- New unit test
  `src/test/java/com/auditlog/application/AuditEventQueryValidationTest.java`
  with one test per rule plus a happy case.

**Design decision locked here.** Use exceptions over `Result<T, E>`:
- Matches the existing domain convention (`AuditEvent` throws
  `IllegalArgumentException`).
- Simplifies T6's `@ExceptionHandler` — Spring already routes thrown
  exceptions through advice; a `Result` would require a sentinel-check at
  the controller seam.
- The `ValidationException` carries the structured `ValidationError`, so
  T6 can translate to JSON without parsing strings.

## Implementation plan

1. **Create `ValidationError`.**
   - Path: `src/main/java/com/auditlog/application/ValidationError.java`.
   - Signature:
     ```java
     public record ValidationError(String code, String message, String field) {
       public ValidationError(String code, String message) { this(code, message, null); }

       public static ValidationError missingFilter() {
         return new ValidationError("MISSING_FILTER",
             "At least one of 'actor' or 'resource' is required.");
       }
       public static ValidationError missingParameter(String field) {
         return new ValidationError("MISSING_PARAMETER",
             "Parameter '" + field + "' is required.", field);
       }
       public static ValidationError invalidTimeWindow() {
         return new ValidationError("INVALID_TIME_WINDOW",
             "'from' must be strictly before 'to'.");
       }
       public static ValidationError windowTooLarge() {
         return new ValidationError("WINDOW_TOO_LARGE",
             "Time window must not exceed 7 days.");
       }
       public static ValidationError limitOutOfRange() {
         return new ValidationError("LIMIT_OUT_OF_RANGE",
             "'limit' must be between 1 and 500.", "limit");
       }
       public static ValidationError conflictingParameters() {
         return new ValidationError("CONFLICTING_PARAMETERS",
             "'cursor' cannot be supplied with filter parameters.");
       }
     }
     ```
   - **Edge case**: keep `field` nullable; some errors are not tied to a
     single parameter (`MISSING_FILTER`, `CONFLICTING_PARAMETERS`).

2. **Create `ValidationException`.**
   - Path: `src/main/java/com/auditlog/application/ValidationException.java`.
   - Signature:
     ```java
     public class ValidationException extends RuntimeException {
       private final ValidationError error;

       public ValidationException(ValidationError error) {
         super(error.message());
         this.error = error;
       }

       public ValidationError error() { return error; }
     }
     ```
   - **Edge case**: keep it `RuntimeException`-derived so call sites are
     not forced to declare it; this matches Spring's idiom.

3. **Add `validate()` to `AuditEventQuery`.**
   - File: `src/main/java/com/auditlog/application/AuditEventQuery.java`.
   - Add (alongside `withFilters`):
     ```java
     private static final Duration MAX_WINDOW = Duration.ofDays(7);

     public AuditEventQuery validate() {
       boolean hasCursor = cursor != null && !cursor.isBlank();
       boolean hasAnyFilter = actor != null || resource != null
                              || from != null || to != null;

       if (hasCursor && hasAnyFilter)
         throw new ValidationException(ValidationError.conflictingParameters());

       if (hasCursor)
         return this; // cursor decode validates the rest

       if ((actor == null || actor.isBlank())
           && (resource == null || resource.isBlank()))
         throw new ValidationException(ValidationError.missingFilter());

       if (from == null)
         throw new ValidationException(ValidationError.missingParameter("from"));
       if (to == null)
         throw new ValidationException(ValidationError.missingParameter("to"));

       if (!from.isBefore(to))
         throw new ValidationException(ValidationError.invalidTimeWindow());

       if (Duration.between(from, to).compareTo(MAX_WINDOW) > 0)
         throw new ValidationException(ValidationError.windowTooLarge());

       if (limit < 1 || limit > 500)
         throw new ValidationException(ValidationError.limitOutOfRange());

       return this;
     }
     ```
   - **Edge case — order of checks matters.** `CONFLICTING_PARAMETERS` runs
     first so a cursor request with stray filters fails with the right
     code, not `MISSING_FILTER`. After that, all subsequent checks assume
     no cursor.
   - **Edge case — blank vs null.** Spring binds an absent query param to
     `null`; an empty `?actor=` binds to `""`. Treat blank as absent.
   - **Edge case — `INVALID_TIMESTAMP` is not raised here.** Add a code
     comment pointing the reader at the API binding boundary (T6's
     `GlobalExceptionHandler.handleTypeMismatch`).

4. **Create the validation unit test.**
   - Path: `src/test/java/com/auditlog/application/AuditEventQueryValidationTest.java`.
   - JUnit 5 + AssertJ. One `@Test` per rule:
     - `validate_acceptsMinimalValidQuery_AC_1_1` — actor set, valid window,
       limit 100, no cursor → no throw, returns same instance.
     - `validate_rejectsCursorWithFilter_AC_2_4` — cursor + actor; assert
       `CONFLICTING_PARAMETERS`, `field == null`.
     - `validate_acceptsCursorAlone_AC_2_4` — cursor only → no throw.
     - `validate_rejectsMissingBothFilters_AC_1_4` — actor and resource null
       → `MISSING_FILTER`.
     - `validate_rejectsMissingFrom_AC_1_3` → `MISSING_PARAMETER` with
       `field == "from"`.
     - `validate_rejectsMissingTo_AC_1_3` → `MISSING_PARAMETER` with
       `field == "to"`.
     - `validate_rejectsFromAfterTo_AC_1_5` → `INVALID_TIME_WINDOW`.
     - `validate_rejectsFromEqualsTo_AC_1_5` → `INVALID_TIME_WINDOW`
       (`isBefore` is strict, so equal timestamps fail).
     - `validate_rejectsWindowOver7Days_AC_1_6` — window = 7 days + 1
       second → `WINDOW_TOO_LARGE`. Boundary test: window = exactly 7 days
       → no throw.
     - `validate_rejectsLimitZero_AC_2_7` → `LIMIT_OUT_OF_RANGE`.
     - `validate_rejectsLimitOver500_AC_2_7` → `LIMIT_OUT_OF_RANGE`.
     - `validate_acceptsLimit1_AC_2_7` → no throw.
     - `validate_acceptsLimit500_AC_2_7` → no throw.
   - Helper: a tiny `query(...)` builder method in the test class so each
     test reads in one line.

5. **Run the new tests.**
   - `./gradlew unitTest --tests AuditEventQueryValidationTest` until
     every method is green.

6. **Confirm no regression.**
   - `./gradlew unitTest archUnitTest integrationTest spotlessCheck` — all
     green. The new files are pure additions; no production caller
     invokes `validate()` yet.
