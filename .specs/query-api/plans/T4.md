# T4 — Repository port: add `findPage(AuditEventQuery)` and JPA implementation

*Extend the `AuditEventRepository` port with a keyset-pagination method and
implement it in the JPA adapter, alongside the existing
`find(AuditEventSearchCriteria)`.*

## Why this task exists

The new query path needs a database-side operation that:

1. Filters by `actor` and/or `resource` and the `[from, to)` window.
2. Applies the keyset compare against the cursor anchor `(ts, id)` when one
   was supplied by the service.
3. Sorts deterministically by `(event_timestamp DESC, id DESC)`.
4. Fetches `LIMIT n+1` so the adapter can report `hasMore` without a
   separate `COUNT(*)` (which would itself breach p95 at 50M rows).
5. Targets only the hot `audit_events` table (never `audit_events_archive`).

The existing `find(AuditEventSearchCriteria)` cannot be evolved in place:
its return type, parameter type, and offset semantics all differ. Adding
`findPage` alongside it keeps both code paths shippable, so T6 can flip
the controller and T7 can drop the legacy method as a separate revertible
PR.

JPA/Hibernate access is confined to the Infrastructure layer (AC-5.2); the
port lives in Application but its only implementation is in
`com.auditlog.infrastructure.persistence`.

## Requirements covered

- **AC-1.1** (Event-driven) WHEN the client sends `GET /audit-events` with
  `from`, `to`, and at least one of `actor`/`resource`, THE SYSTEM SHALL
  return events ordered by `event_timestamp` DESC, then `id` DESC.
- **AC-1.2** (Event-driven) WHEN both `actor` and `resource` are supplied,
  THE SYSTEM SHALL return only events matching both filters (logical AND).
- **AC-1.8** (Ubiquitous) THE SYSTEM SHALL treat `from` as inclusive and `to`
  as exclusive (`[from, to)`).
- **AC-2.3** (Event-driven) WHEN the client sends a request with a valid
  `cursor`, THE SYSTEM SHALL return the next page of items strictly older
  than the cursor's `(event_timestamp, id)` anchor, while applying the
  filter set encoded in the cursor.
- **AC-3.2** (Ubiquitous) THE SYSTEM SHALL execute queries through the
  composite indexes, verified with `EXPLAIN ANALYZE`.
- **AC-4.1** (Ubiquitous) THE SYSTEM SHALL include `id`, `timestamp`,
  `actor`, `action`, `resource`, `outcome`, and `context` on every item.
- **AC-4.2** (Ubiquitous) THE SYSTEM SHALL serialize `timestamp` as the same
  instant the event was recorded with, in UTC.
- **AC-4.3** (Ubiquitous) THE SYSTEM SHALL NOT include rows from
  `audit_events_archive`.
- **AC-5.2** (Ubiquitous) THE SYSTEM SHALL keep all JPA/Hibernate access
  inside the Infrastructure layer, behind the existing
  `AuditEventRepository` port.

## Design references — extracts inlined

### Pagination strategy → Continuation predicate

```sql
WHERE  event_timestamp >= :from
  AND  event_timestamp <  :to
  AND  (:actor    IS NULL OR actor    = :actor)
  AND  (:resource IS NULL OR resource = :resource)
  AND  (
        :cursor_ts IS NULL
        OR event_timestamp <  :cursor_ts
        OR (event_timestamp = :cursor_ts AND id < :cursor_id)
      )
ORDER  BY event_timestamp DESC, id DESC
LIMIT  :limit + 1;
```

Written as `(event_timestamp, id) < (:cursor_ts, :cursor_id)` in row-form
for clarity; the expanded form above is what we emit because PostgreSQL
plans it more reliably against the composite index.

### Page assembly — `LIMIT n+1`

Each page runs **one** query with `LIMIT limit + 1`. The (limit+1)-th row,
if present, is dropped from `items` and used solely to set `hasMore = true`
and to source the next `nextCursor`. `nextCursor` is built from the last
**kept** row.

### Sort & determinism

Final ORDER BY for every query: `event_timestamp DESC, id DESC`. The table
is immutable (V2 trigger blocks UPDATEs), so the `(timestamp, id)` ordering
of any row is fixed for the lifetime of the row. New events ingested *after*
a cursor is issued sort *before* the cursor and therefore are not visited by
that cursor's continuation.

## Current state

- **Port**: `com.auditlog.application.AuditEventRepository` exposes
  `AuditEvent save(AuditEvent)` and `List<AuditEvent> find(AuditEventSearchCriteria)`.
- **Adapter**: `com.auditlog.infrastructure.persistence.JpaAuditEventRepository`
  implements both methods. `find(...)` uses JPA Criteria API with
  `actor`, `resource`, and `event_timestamp` range predicates, orders by
  `event_timestamp DESC`, then applies `setFirstResult(offset)` and
  `setMaxResults(limit)`.
- **Entity**: `com.auditlog.infrastructure.persistence.JpaAuditEventEntity`
  is package-private and maps the `audit_events` columns. It exposes
  `toDomain()` / `fromDomain(...)` mappers.
- **Mapping to view**: `com.auditlog.application.AuditEventView.fromDomain(AuditEvent)`
  converts a domain object to the DTO used by `AuditEventPage.items`.
- **Indexes**: after T1 the table has
  `idx_audit_events_actor_ts_id (actor, event_timestamp DESC, id DESC)` and
  `idx_audit_events_resource_ts_id (resource, event_timestamp DESC, id DESC)`.
  Either is selectable by the new SQL.
- **Integration tests**: `AuditEventPersistenceIntegrationTest` exists and
  must remain unchanged.

## Target state

- **Port** gains `AuditEventPage findPage(AuditEventQuery query);`.
- **Adapter** implements `findPage(...)` using a native SQL query that
  matches the continuation predicate above, with `LIMIT :limit + 1` and
  slicing-in-the-adapter logic.
- New integration test
  `AuditEventQueryRepositoryIntegrationTest` covers 3+ pages, ordering,
  same-instant tiebreaker, concurrent inserts at the head, and an
  EXPLAIN-ANALYZE assertion proving an index scan on one of the new V3
  indexes.
- The old `find(...)` method and `AuditEventPersistenceIntegrationTest`
  stay unchanged.

## Implementation plan

1. **Add the port method.**
   - File: `src/main/java/com/auditlog/application/AuditEventRepository.java`.
   - Append:
     ```java
     AuditEventPage findPage(AuditEventQuery query);
     ```
   - **Edge case**: keep the existing `save` and `find` signatures
     untouched. T7 owns their removal.

2. **Implement `findPage` in the JPA adapter.**
   - File:
     `src/main/java/com/auditlog/infrastructure/persistence/JpaAuditEventRepository.java`.
   - Add this method below the existing `find(...)`:
     ```java
     @Override
     @Transactional(readOnly = true)
     public AuditEventPage findPage(AuditEventQuery query) {
       // AC-4.3 — read only from the hot table.
       final String sql = """
           SELECT *
             FROM audit_events
            WHERE event_timestamp >= :from
              AND event_timestamp <  :to
              AND (:actor    IS NULL OR actor    = :actor)
              AND (:resource IS NULL OR resource = :resource)
              AND (
                    :cursor_ts IS NULL
                    OR event_timestamp <  :cursor_ts
                    OR (event_timestamp = :cursor_ts AND id < :cursor_id)
                  )
            ORDER BY event_timestamp DESC, id DESC
            LIMIT :limit_plus_one
           """;

       int limit = query.limit();
       Instant from   = query.from();
       Instant to     = query.to();
       String actor   = query.actor();
       String resource= query.resource();
       Instant cursorTs = null;
       UUID    cursorId = null;
       // Cursor envelope arrives already-decoded from T5 — see contract below.

       @SuppressWarnings("unchecked")
       List<JpaAuditEventEntity> rows = entityManager
           .createNativeQuery(sql, JpaAuditEventEntity.class)
           .setParameter("from",     Timestamp.from(from))
           .setParameter("to",       Timestamp.from(to))
           .setParameter("actor",    actor)
           .setParameter("resource", resource)
           .setParameter("cursor_ts", cursorTs == null ? null : Timestamp.from(cursorTs))
           .setParameter("cursor_id", cursorId)
           .setParameter("limit_plus_one", limit + 1)
           .getResultList();

       boolean hasMore = rows.size() > limit;
       List<JpaAuditEventEntity> kept = hasMore ? rows.subList(0, limit) : rows;

       List<AuditEventView> items = kept.stream()
           .map(JpaAuditEventEntity::toDomain)
           .map(AuditEventView::fromDomain)
           .toList();

       String nextCursor = null;
       if (hasMore) {
         JpaAuditEventEntity last = kept.get(kept.size() - 1);
         nextCursor = AuditEventCursor.encode(new AuditEventCursor(
             last.getEventTimestamp(), last.getId(),
             actor, resource, from, to, AuditEventCursor.V));
       }
       return new AuditEventPage(items, nextCursor, hasMore);
     }
     ```
   - **Contract with T5.** The service decodes the cursor *before* calling
     `findPage`. It must call `query.withFilters(c.actor(), c.resource(),
     c.from(), c.to())` to inject the envelope fields onto the query, and
     it must pass the cursor anchor `(c.ts(), c.id())` *somehow*. Two
     options:
     - **Option A** (simpler) — add two parameters to `findPage`:
       `findPage(AuditEventQuery query, Instant cursorTs, UUID cursorId)`.
       Pass nulls for the first page. Update the port accordingly.
     - **Option B** — extend `AuditEventQuery` with optional decoded
       anchor fields (`Instant cursorTs, UUID cursorId`). Hides the split
       behind one parameter; bloats the record.
     - **Recommended: Option A.** It keeps `AuditEventQuery` as the public
       request shape and pushes the cursor anchor into the adapter
       signature where it belongs.
     - The pseudocode above reflects Option A: replace the two `null`
       initializers with method parameters. Update the port signature to
       `AuditEventPage findPage(AuditEventQuery query, Instant cursorTs, UUID cursorId);`.
   - **Edge case — parameter binding.** Hibernate's native query binding
     handles `null` for `IS NULL` shortcut params; verify by running the
     "no cursor" test path. If null binding requires explicit type hints,
     use `setParameter("cursor_ts", cursorTs, TemporalType.TIMESTAMP)` or
     equivalent.
   - **Edge case — Instant ↔ TIMESTAMPTZ.** Use `Timestamp.from(instant)`
     so JDBC binds a UTC timestamp regardless of session TZ. The column
     type from V1 is `TIMESTAMPTZ`.
   - **Edge case — never touch the archive.** The SQL `FROM audit_events`
     and the leading comment lock this. Do not add any `UNION` or
     archive-fallback logic.

3. **Verify the package-private entity is accessible.**
   - `JpaAuditEventEntity` is package-private (it lives in the same package
     as `JpaAuditEventRepository`); the adapter already references it for
     `find(...)`. No visibility changes needed.

4. **Compile and run unit tests.**
   - `./gradlew compileJava unitTest` — green. No unit-test changes for
     this task; the adapter is integration-tested.

5. **Create the integration test.**
   - Path:
     `src/test/java/com/auditlog/infrastructure/persistence/AuditEventQueryRepositoryIntegrationTest.java`.
   - Copy the Testcontainers bootstrap from `AuditEventPersistenceIntegrationTest`
     (`@SpringBootTest`, `@Testcontainers`, `@ServiceConnection` with
     `PostgreSQLContainer<>("postgres:16-alpine")`).
   - Test methods:
     1. `findPage_seedsAndPagesThreeFullPagesWithoutDuplicatesOrSkips`
        Seed 250 rows for actor `"svc:billing"` over a 1-hour window with
        monotonically increasing `event_timestamp` (1-second spacing).
        Fetch with `limit = 100`, no cursor → assert
        `items.size() == 100`, `hasMore == true`,
        `nextCursor != null`, and ordering. Decode cursor, build next
        query with `(cursorTs, cursorId)` set, fetch → next 100, then
        next 50 → `hasMore == false`. Concatenate the three pages,
        assert size 250 and no duplicate ids.
     2. `findPage_sameInstantRowsAreOrderedByIdDesc`
        Insert two rows with identical `event_timestamp` and distinct
        UUIDs. Assert the returned pair is ordered by `id DESC`.
     3. `findPage_concurrentInsertAtHeadIsNotVisitedByCursor`
        Seed 200 rows. Fetch page 1 (`limit = 100`). Insert a new row
        with `event_timestamp = Instant.now()` (strictly newer than any
        seeded row). Fetch page 2 with the cursor → assert the new row
        is *not* in the result.
     4. `findPage_combinedActorAndResourceFilter_returnsIntersection`
        Seed rows mixing actors and resources. Query with both filters
        set → assert every returned row matches both.
     5. `findPage_explainAnalyzeUsesNewActorIndex`
        Seed ≥ 1,000 rows. Run
        `entityManager.createNativeQuery("EXPLAIN (ANALYZE, BUFFERS) " + SQL)`
        bound with `actor` set, `resource` null. Concatenate the result
        rows into a string and assert it contains
        `"idx_audit_events_actor_ts_id"`.
     6. `findPage_explainAnalyzeUsesNewResourceIndex` — same but with
        `resource` set.
   - **Edge case — small dataset planner.** With ~1,000 rows PG may still
     pick a seq scan. Mitigate by either (a) seeding 5,000 rows in the
     EXPLAIN tests, or (b) running `SET enable_seqscan = off;` for the
     EXPLAIN-asserting tests only (do not let this leak to functional
     tests). Prefer (a).
   - **Edge case — clock skew across the test.** When asserting "newer
     than any seeded row" for the concurrent-insert test, take a
     `Instant.now()` snapshot before seeding and seed strictly before
     that instant.
