# T5 — Application service: `AuditEventQueryService.queryPage(...)`

*Add a new orchestration method on the existing `AuditEventQueryService`
that validates, decodes/encodes cursors, and calls `findPage`. The legacy
method stays.*

## Why this task exists

The new query path needs an Application-layer orchestrator that:

1. Validates a first-page request (no cursor) via
   `AuditEventQuery.validate()` (T3).
2. For a continuation request (cursor present), rejects any stray filter
   params (AC-2.4) and decodes the cursor envelope (AC-2.3, AC-2.5).
3. Reapplies the cursor's encoded filters onto the query.
4. Calls the new repository port `findPage(...)` (T4).
5. Returns the resulting `AuditEventPage` unchanged — the adapter has
   already built `nextCursor` and `hasMore`.

Layering matters: the service is Application-only, with no Spring/JPA/HTTP
types in its imports (AC-5.1). The cursor encoding/decoding lives in
`AuditEventCursor` (T2), which also stays under
`com.auditlog.application`. T8 will lock both boundaries via ArchUnit.

The legacy `find(AuditEventSearchCriteria)` method on the service stays
in place until T7 removes it. Adding `queryPage(...)` alongside lets T6
flip the controller and T7 drop the legacy method as separate revertible
PRs.

## Requirements covered

- **AC-2.1** (Ubiquitous) THE SYSTEM SHALL return a JSON envelope of the form
  `{ "items": [...], "nextCursor": <string|null>, "hasMore": <boolean> }`.
- **AC-2.2** (Ubiquitous) THE SYSTEM SHALL set `hasMore = (nextCursor != null)`.
- **AC-2.3** (Event-driven) WHEN the client sends a request with a valid
  `cursor` parameter, THE SYSTEM SHALL return the next page of items
  strictly older than the cursor's `(event_timestamp, id)` anchor, while
  applying the filter set encoded in the cursor.
- **AC-2.4** (Unwanted) IF a `cursor` is supplied together with any of
  `actor`, `resource`, `from`, or `to`, THEN THE SYSTEM SHALL return HTTP 400.
- **AC-2.5** (Unwanted) IF the supplied `cursor` is malformed, tampered, or
  not parseable, THEN THE SYSTEM SHALL return HTTP 400.
- **AC-2.8** (Ubiquitous) THE SYSTEM SHALL produce an opaque, URL-safe
  `nextCursor` string.
- **AC-3.3** (Ubiquitous) THE SYSTEM SHALL be side-effect free: a query
  request SHALL NOT write any rows or mutate persistent state.
- **AC-5.1** (Ubiquitous) THE SYSTEM SHALL define cursor and request types in
  the Application layer; the API layer SHALL only translate HTTP
  ↔ Application DTOs.

## Design references — extracts inlined

### Cursor format — what `decode` returns

```jsonc
{
  "ts":       "2026-05-03T14:22:09.871Z",
  "id":       "5b9c…-uuid",
  "actor":    "svc:billing",
  "resource": null,
  "from":     "2026-04-26T00:00:00Z",
  "to":       "2026-05-03T00:00:00Z",
  "v":        1
}
```

The service decodes once per request and forwards `(ts, id)` as the
anchor parameters to `findPage(...)`, plus the four filter fields as
the query's `actor`/`resource`/`from`/`to`.

### Pagination strategy → Page assembly (where the work happens)

Each page runs **one** query with `LIMIT limit + 1`. The slicing and
`nextCursor` assembly live in the adapter — the service is a thin
orchestrator. Why: the adapter is the only layer that knows it fetched
`limit + 1`.

### Integration with arch layers → Application layer

```
Application layer  (com.auditlog.application)
  Service:
    AuditEventQueryService
      · validates request
      · decodes cursor (if any) and reapplies filters
      · calls AuditEventRepository.findPage(query, cursorTs, cursorId)
      · returns AuditEventPage unchanged
```

## Current state

- `com.auditlog.application.AuditEventQueryService` exists and exposes
  `List<AuditEventView> find(AuditEventSearchCriteria criteria)` —
  the legacy method. It is annotated `@Service` and constructor-injected
  with `AuditEventRepository`.
- `AuditEventQuery.validate()` (T3) throws `ValidationException` carrying a
  `ValidationError`.
- `AuditEventCursor.decode(String)` (T2) throws `IllegalArgumentException`
  with marker message `"INVALID_CURSOR"` on bad input.
- `AuditEventRepository.findPage(AuditEventQuery, Instant cursorTs, UUID cursorId)`
  (T4) is the port the service calls.

## Target state

- `AuditEventQueryService` gains `AuditEventPage queryPage(AuditEventQuery query)`.
- The legacy `find(...)` method is unchanged.
- New unit test `AuditEventQueryServiceTest` exercises the orchestration
  with a hand-rolled fake repository.
- No imports of `org.springframework.web.*`, `jakarta.persistence.*`, or
  `org.springframework.transaction.*` in `AuditEventQueryService`.
  (`@Service` and the existing `@Transactional` on `find(...)` are fine —
  they're Spring stereotypes, not framework leakage; the existing class
  already uses them and T8 won't ban Spring stereotypes from the service.)

## Implementation plan

1. **Add `queryPage` to `AuditEventQueryService`.**
   - File: `src/main/java/com/auditlog/application/AuditEventQueryService.java`.
   - Method:
     ```java
     public AuditEventPage queryPage(AuditEventQuery query) {
       Objects.requireNonNull(query, "query");

       boolean hasCursor = query.cursor() != null && !query.cursor().isBlank();
       Instant cursorTs = null;
       UUID    cursorId = null;
       AuditEventQuery effective = query;

       if (hasCursor) {
         // AC-2.4 — cursor and any filter param are mutually exclusive.
         if (query.actor() != null || query.resource() != null
             || query.from() != null || query.to() != null) {
           throw new ValidationException(ValidationError.conflictingParameters());
         }
         AuditEventCursor c;
         try {
           c = AuditEventCursor.decode(query.cursor());
         } catch (IllegalArgumentException e) {
           // AC-2.5 — re-wrap as a structured ValidationError so the API
           // layer (T6) maps it through the single advice path.
           throw new ValidationException(
               new ValidationError("INVALID_CURSOR", "Cursor is invalid.", "cursor"));
         }
         effective = query.withFilters(c.actor(), c.resource(), c.from(), c.to());
         cursorTs = c.ts();
         cursorId = c.id();
       } else {
         effective.validate(); // throws ValidationException on bad shape
       }

       // AC-3.3 — repository.findPage is read-only.
       return repository.findPage(effective, cursorTs, cursorId);
     }
     ```
   - **Edge case — `IllegalArgumentException` swallow.** Cursor decode
     throws `IllegalArgumentException`; the catch above converts it into
     a `ValidationException` so T6 only needs one `@ExceptionHandler`.
     Do *not* let raw `IllegalArgumentException` reach the controller —
     that would couple T6 to T2's internal exception type.
   - **Edge case — limit on cursor path.** The cursor envelope does not
     carry `limit`; the caller may legitimately change `limit` between
     pages. Use `query.limit()` as-is. T6 ensures `limit` is in range
     (or that defaulting happened earlier); the validator's
     `limitOutOfRange` rule does not run on the cursor branch by design.
     If a stricter check is desired, add an explicit `if (limit < 1 ||
     limit > 500) throw …` *after* the branch — recommended, since the
     API layer might forward a bad value.
   - **Edge case — defensive null check.** Reject `query == null` early
     so the stack trace is obvious in tests.

2. **Verify the file has no leaky imports.**
   - `grep -E '^import' src/main/java/com/auditlog/application/AuditEventQueryService.java`.
   - Expected: `java.*`, `com.auditlog.application.*`. Disallowed:
     `org.springframework.web.*`, `jakarta.persistence.*`,
     `org.hibernate.*`. `org.springframework.stereotype.Service` and
     `org.springframework.transaction.annotation.Transactional` are
     allowed because the file already uses them and the ArchUnit rules
     do not forbid Spring stereotypes from Application classes.

3. **Create the unit test class with a hand-rolled fake.**
   - Path: `src/test/java/com/auditlog/application/AuditEventQueryServiceTest.java`.
   - The project does not standardize on Mockito for unit tests
     (existing `AuditEventTest` is plain JUnit). Use a hand-rolled fake
     for clarity:
     ```java
     static final class FakeRepository implements AuditEventRepository {
       Function<Call, AuditEventPage> response = call ->
           new AuditEventPage(List.of(), null, false);
       Call lastCall;

       record Call(AuditEventQuery query, Instant cursorTs, UUID cursorId) {}

       @Override public AuditEventPage findPage(AuditEventQuery q,
                                                Instant cursorTs,
                                                UUID cursorId) {
         lastCall = new Call(q, cursorTs, cursorId);
         return response.apply(lastCall);
       }
       @Override public AuditEvent save(AuditEvent e) { throw new UnsupportedOperationException(); }
       @Override public List<AuditEvent> find(AuditEventSearchCriteria c) { throw new UnsupportedOperationException(); }
     }
     ```
   - **Edge case**: the fake must still satisfy the full
     `AuditEventRepository` interface — including the legacy `find`
     method. T7 will simplify it once `find` is gone.

4. **Write the unit tests.**
   - Cases (each one method):
     - `queryPage_happyPath_firstPage_returnsAdapterResult`
       Fake returns `(items=[3 rows], nextCursor=null, hasMore=false)`.
       Service returns that envelope. Assert `lastCall.cursorTs == null`,
       `lastCall.cursorId == null`, and the effective query reaches the
       fake unchanged.
     - `queryPage_happyPath_multiPage_propagatesNextCursor`
       Fake returns `(items=[100 rows], nextCursor="…", hasMore=true)`.
       Assert `hasMore == true`, `nextCursor != null`.
     - `queryPage_rejectsCursorWithActor_throwsConflictingParameters`
       Build `AuditEventQuery` with both `cursor` and `actor` set; expect
       `ValidationException` with `error.code() == "CONFLICTING_PARAMETERS"`.
       Verify the fake was *not* called.
     - `queryPage_rejectsCursorWithFrom_throwsConflictingParameters` —
       same with `from` set.
     - `queryPage_rejectsMalformedCursor_throwsInvalidCursor`
       Pass `cursor = "!!not-base64!!"`; expect `ValidationException` with
       `code = "INVALID_CURSOR"`, `field = "cursor"`.
     - `queryPage_decodesCursorAndAppliesFiltersOntoEffectiveQuery`
       Encode a valid cursor via `AuditEventCursor.encode(...)`. Pass it
       as `cursor`, leave all filter params null. Assert
       `lastCall.query.actor()` / `resource()` / `from()` / `to()` match
       the cursor's envelope, and `cursorTs` / `cursorId` match.
     - `queryPage_forwardsValidationFailures_missingFilter`
       No cursor, no actor/resource; expect `MISSING_FILTER`. Fake not
       called.
     - `queryPage_forwardsValidationFailures_windowTooLarge`
       Window = 8 days; expect `WINDOW_TOO_LARGE`. Fake not called.
   - **Edge case**: at least one test should assert that on the cursor
     branch, `validate()` is *not* called (i.e. a cursor request whose
     embedded filters would individually fail `validate()` — e.g.
     window > 7 days — still succeeds). The auditor scenario: a cursor
     issued from a previous session must remain usable even if the
     window rule has tightened. (Confirm with reviewers; if undesired,
     drop this case.)

5. **Run the new tests.**
   - `./gradlew unitTest --tests AuditEventQueryServiceTest` until green.

6. **Run the full pipeline.**
   - `./gradlew unitTest integrationTest archUnitTest spotlessCheck` — all
     green.
   - No production caller invokes `queryPage` yet; T6 wires it up.
