# T9 — Performance verification at 50M rows

*Discharge AC-3.1 and AC-3.2 with reproducible evidence before the feature
merges to master.*

## Why this task exists

Every other task verifies its own behavioral slice via unit and
integration tests, but the two performance ACs cannot be discharged by
Testcontainers at the scale they specify. PostgreSQL's planner picks
different strategies at 50M rows than at 250 — a seq scan that costs
milliseconds in CI can break p95 in production. T9 produces the
load-scale evidence the rest of the work cannot.

This is the final gate before the feature branch merges. If T9 finds a
shape that misses p95 ≤ 300ms, the recommended remediation is the
partial-index option from the design (`Combined actor + resource
queries`), filed as a follow-up — *do not* silently merge a feature that
fails its performance AC.

The task is documentation-and-evidence only: no production code,
migration, or test ships from this task. The output is a section
appended to `NOTES.md`, per AGENTS.md ("NOTES.md contains history of
already performed actions").

## Requirements covered

- **AC-3.1** (Ubiquitous) THE SYSTEM SHALL hold p95 ≤ 300ms for any
  compliant request when `audit_events` contains 50M rows, measured
  server-side.
- **AC-3.2** (Ubiquitous) THE SYSTEM SHALL execute queries through the
  composite indexes, verified with `EXPLAIN ANALYZE` on a 50M-row
  dataset.
- *Open Question #8* (requirements.md → Open questions):
  > Do we have a 50M-row dataset (synthetic or anonymised) available for
  > the EXPLAIN ANALYZE / p95 measurement required by AC-3.1 and AC-3.2,
  > or does generating one fall within this feature?

  T9 answers: generation falls within this feature.

## Design references — extracts inlined

### Indexes → Combined `actor + resource` queries

> No combined `(actor, resource, event_timestamp, id)` index. PostgreSQL
> is expected to pick the more selective single-column index — typically
> `actor` — and filter `resource` from the heap. … This **must be
> verified** with `EXPLAIN ANALYZE` against a 50M-row dataset before
> sign-off (AC-3.2). If selectivity proves insufficient for some hot
> actor, add a partial index targeting that actor rather than a global
> combined index.

### Pagination strategy → Why keyset (the cost claim being measured)

> Cost is `O(log n + page)` regardless of how deep the user has paged,
> because the index lets PG seek directly to the `(ts, id)` anchor.

T9 specifically measures *deep* pages (page 10 of each shape) to confirm
this property in practice, not just in theory.

## Implementation plan

1. **Provision a local PG 16 instance with enough disk.**
   - Pull the matching image: `docker pull postgres:16-alpine` (same
     version as Testcontainers).
   - Start a long-running container with explicit volume:
     ```bash
     mkdir -p ~/audit-perf-pg
     docker run -d --name audit-perf-pg \
       -e POSTGRES_PASSWORD=postgres -e POSTGRES_USER=postgres \
       -e POSTGRES_DB=audit \
       -p 55432:5432 -v ~/audit-perf-pg:/var/lib/postgresql/data \
       postgres:16-alpine
     ```
   - Disk: ~10 GB free. Each audit row is ~200–400 bytes after TOAST;
     50M rows + indexes lands around 12–20 GB. Adjust volume location
     if `~` is on a small disk.
   - **Edge case — Docker memory.** Bump Docker Desktop's resource
     allocation to ≥ 8 GB RAM and ≥ 4 cores before benchmarking so the
     PG container is not throttled.

2. **Apply Flyway migrations V1–V4 to the perf DB.**
   - From the repo root:
     ```bash
     ./gradlew flywayMigrate \
       -Pflyway.url=jdbc:postgresql://localhost:55432/audit \
       -Pflyway.user=postgres -Pflyway.password=postgres
     ```
   - Confirm the index list matches the post-T7 expected state:
     `psql -h localhost -p 55432 -U postgres -d audit -c '\d+ audit_events'`.

3. **Write a one-off seed script.**
   - Path: `tools/perf-seed/` (outside `src/main` so Spotless / unit
     tests do not run against it; not committed to the production
     branch unless useful for repeatability).
   - Approach: a small Java main (e.g. `PerfSeed.java`) or Python
     script that streams ~50M rows of CSV to stdout, which is then
     piped into `psql \copy` for fastest ingest.
   - Distribution:
     - `id`: random UUID v4.
     - `event_timestamp`: uniformly distributed over a 30-day window
       ending at "now". This keeps the 7-day window queries hitting
       roughly `50M × 7/30 ≈ 11.7M` rows.
     - `actor`: drawn from a Zipfian sample over ~5,000 distinct
       values. Include one "hot actor" representing ~5% of traffic to
       exercise the AC-3.2 worst case.
     - `resource`: drawn uniformly over ~50,000 distinct values.
     - `action`: one of ~20 plausible verbs (e.g. `invoice.created`,
       `user.login`).
     - `outcome`: 95% `SUCCESS`, 4% `DENIED`, 1% `ERROR`.
     - `context`: a small `jsonb` object, e.g.
       `{"amount": <float>, "currency": "EUR"}`.
   - **Edge case — seed reproducibility.** Use a fixed RNG seed so the
     same data can be regenerated for re-runs.
   - **Edge case — TIMESTAMPTZ formatting.** PostgreSQL's `COPY` accepts
     ISO-8601 with offsets; emit `Z`-suffixed UTC timestamps.

4. **Load the data via `psql \copy`.**
   - Direct pipe (recommended — avoids a 20 GB intermediate file):
     ```bash
     java -jar tools/perf-seed/perf-seed.jar | \
       psql -h localhost -p 55432 -U postgres -d audit \
            -c '\copy audit_events (id, event_timestamp, actor, action, resource, outcome, context) FROM STDIN WITH (FORMAT csv)'
     ```
   - Expected wall-clock: 5–20 minutes on a developer laptop.
   - **Edge case — immutability trigger.** V2 installs a trigger that
     blocks UPDATE on `audit_events`. INSERT is allowed; `COPY ... FROM`
     is INSERT-equivalent and not blocked. Verify if uncertain.

5. **Refresh planner statistics.**
   - `psql -h localhost -p 55432 -U postgres -d audit -c 'ANALYZE audit_events;'`.
   - Wait a few seconds; this is fast at 50M rows but not instant.

6. **Capture `EXPLAIN (ANALYZE, BUFFERS)` plans.**
   - For each of these four shapes, run the actual SQL produced by
     `JpaAuditEventRepository.findPage` with bound parameters:
     1. **actor-only, 7-day window, page 1**
        Parameters: `actor = '<hot actor>'`, `resource = null`,
        `from = now-7d`, `to = now`, `cursor_ts = null`, `cursor_id =
        null`, `limit = 100`.
     2. **resource-only, 7-day window, page 1**
        `actor = null`, `resource = '<random resource>'`, same window.
     3. **actor + resource, 7-day window, page 1**
        Both filters set; uses the hot actor + a resource that has
        traffic in-window.
     4. **deep cursor, page 10 of each of the above**
        Drive the keyset forward 9 pages, then capture EXPLAIN for the
        10th. Confirms keyset cost stays `O(log n + page)` deep.
   - Save plans to `tools/perf-output/plan-{shape}.txt` (local; not
     committed).
   - **Edge case — plan stability.** Run each plan three times and keep
     the median. The first run pays a buffer-cache miss; the later runs
     reflect steady-state.
   - **Verification criterion.** Every plan must show an
     `Index Scan` or `Index Only Scan` against either
     `idx_audit_events_actor_ts_id` or `idx_audit_events_resource_ts_id`
     for the seek; any plan showing `Seq Scan on audit_events` fails
     AC-3.2.

7. **Capture wall-clock p95 latency.**
   - Start the app pointing at the perf DB:
     ```bash
     SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:55432/audit \
     SPRING_DATASOURCE_USERNAME=postgres \
     SPRING_DATASOURCE_PASSWORD=postgres \
     ./gradlew bootRun
     ```
   - For each of the four query shapes from step 6, run a load
     generator. Recommended: `wrk` with 4 threads, 50 connections,
     60 s — yields > 1,000 requests on a typical query.
     ```bash
     wrk -t4 -c50 -d60s --latency \
       'http://localhost:8080/audit-events?actor=<hot>&from=<t0>&to=<t1>&limit=100'
     ```
   - Capture from each `wrk` output: total requests, p50, p95, p99,
     max. The keyset deep-page test needs the encoded cursor in the
     URL; capture that from a previous response.
   - **Edge case — warm-up.** Discard the first 10 seconds of each run
     (wrk's `--latency` includes the cold start). Either run a 5-second
     warm-up first, then the measured 60-second run, or rely on `wrk`'s
     full-window p95.
   - **Verification criterion.** Every shape's p95 ≤ 300ms.

8. **Document the results in `NOTES.md`.**
   - Append a new section:
     ```markdown
     ## Audit query keyset performance — 2026-MM-DD

     Dataset: ~50M synthetic rows over a 30-day window. PG 16 in
     Docker on <hardware>. Indexes after V4:
     `idx_audit_events_actor_ts_id`, `idx_audit_events_resource_ts_id`,
     `idx_audit_events_timestamp`.

     | Shape                                | p95 (ms) | Index used                        |
     |--------------------------------------|---------:|-----------------------------------|
     | actor-only, 7d, page 1               |        … | idx_audit_events_actor_ts_id      |
     | resource-only, 7d, page 1            |        … | idx_audit_events_resource_ts_id   |
     | actor + resource, 7d, page 1         |        … | idx_audit_events_actor_ts_id (heap-filter on resource) |
     | actor-only, 7d, cursor page 10       |        … | idx_audit_events_actor_ts_id      |
     | resource-only, 7d, cursor page 10    |        … | idx_audit_events_resource_ts_id   |

     EXPLAIN ANALYZE outputs archived at <internal link> /
     attached to PR #<n>.

     Outcome: AC-3.1 and AC-3.2 [met | not met for shape X — see issue
     #<n>].
     ```
   - **Edge case — date.** Use the literal date the measurements ran;
     do not pre-date.

9. **Handle a failing shape.**
   - If any shape misses 300ms p95 or fails the EXPLAIN criterion:
     1. Capture the failing plan separately.
     2. File a follow-up issue describing: the shape, the dataset, the
        observed p95, the EXPLAIN plan, and the design.md
        partial-index remediation.
     3. Add a "Blocker" note in `NOTES.md` linking the issue.
     4. Do **not** merge the feature until the follow-up either lands
        or is explicitly accepted as known risk by reviewers.

10. **Tear down the perf environment.**
    - `docker stop audit-perf-pg && docker rm audit-perf-pg`.
    - `rm -rf ~/audit-perf-pg`.
    - Keep `tools/perf-seed/` and `tools/perf-output/` outside of the
      production source tree so they don't accidentally ship.
